# 01. Apache Kafka 핵심 개념

> F-lab Apache Kafka 강의 자료 정리. 실습은 [02-cli-lab.md](02-cli-lab.md), [Python 예제](../python/README.md) 참고.

## 1. Kafka 를 쓰는 이유

| 특징 | 설명 |
| --- | --- |
| **높은 처리량** | 파티션 단위 병렬 처리로 동일 시간당 처리량 증가. 파티션 하나당 컨슈머 하나가 붙으므로, 컨슈머를 늘리려면 파티션도 늘려야 한다. |
| **확장성** | 브로커 Scale-out / Scale-in 가능, 무중단 운영 가능. 단, **파티션은 Scale-in(축소) 불가**. |
| **영속성** | 프로듀서가 종료되어도 데이터가 사라지지 않음. 파일시스템에 저장하지만 OS 페이지 캐시를 활용하므로 느리지 않다. 브로커가 갑자기 종료되어도 안전하게 재처리 가능. |
| **고가용성** | 일반적으로 3대 이상의 브로커로 클러스터를 구성하고 데이터를 복제한다. |

```
Producer A ─┐                         ┌─ Consumer 0 ┐
Producer B ─┼─▶ Broker 0 / 1 / 2 ─────┼─ Consumer 1 ├─ Consumer Group A
            │   (TopicA, TopicB 의     └─ Consumer 2 ┘
            │    파티션들이 분산 저장)
```

## 2. 브로커 클러스터

### 브로커
- 클라이언트(프로듀서/컨슈머)와 데이터를 주고받는 서버 프로세스
- 프로듀서에게 받은 데이터를 **분산 · 복제 · 저장**
- 일반적 구성: 서버 1대 = 브로커 1개, 3대 이상을 1개 클러스터로 운영 (대규모 서비스는 50대 이상)

### 컨트롤러
- 여러 브로커 중 한 대가 컨트롤러 역할
- 다른 브로커의 상태를 체크하고, 브로커가 빠지면(장애 / Scale-in) 그 브로커의 **리더 파티션을 재분배**
- 컨트롤러 장애 시 다른 브로커가 대체

> **강의 자료와 실습 환경의 차이** — 강의 자료는 ZooKeeper 기반이지만, 이 레포의 Kafka 4.x 는 ZooKeeper 가
> 완전히 제거되고 **KRaft** 모드로 동작한다. 컨트롤러 쿼럼이 메타데이터를 `__cluster_metadata` 토픽에 직접 관리한다.
> 실습 컨테이너는 브로커와 컨트롤러 역할을 한 프로세스가 함께 수행한다 (`KAFKA_PROCESS_ROLES: broker,controller`).

### 데이터 저장
- `server.properties` 의 `log.dirs` 경로에 저장 (이 레포: 컨테이너 `/var/lib/kafka/data` = 호스트 `./data`)
- `<토픽명>-<파티션번호>` 디렉토리가 생성됨 (예: `hello.kafka-0/`)
- 디렉토리 안의 데이터는 **세그먼트** 파일 단위로 나뉜다. 파일명은 그 세그먼트의 시작 오프셋.

```
hello.kafka-0/
├── 00000000000000000000.log   offset 0 ~ 9
├── 00000000000000000010.log   offset 10 ~ 19
└── 00000000000000000020.log   offset 20 ~      ← ACTIVE 세그먼트 (현재 쓰기 중)
```

### 데이터 복제 (Replication)
- 일부 브로커 장애 시 데이터 유실 방지
- **파티션 단위**로 복제 개수 지정: `replication factor` (최소 1 = 복제 없음 ~ 최대 브로커 수)
- 리더 파티션에 쓰고, 팔로워 파티션들이 복제해 감
- **ISR (In-Sync Replicas)**: 리더와 동기화가 완료된 레플리카 집합
- 리더가 있는 브로커가 다운되면 팔로워 중 하나가 리더로 승급
- **프로듀서/컨슈머는 리더 파티션과만 통신**

```
Broker 0                 Broker 1                 Broker 2
TopicA Partition 0       TopicA Partition 0       TopicA Partition 0
   (Leader)       ──▶       (Follower)     ──▶       (Follower)
```

### 데이터 삭제
- **오직 브로커만** 삭제 가능 (프로듀서/컨슈머는 불가)
- 특정 레코드를 골라서 삭제할 수 없고 **세그먼트 파일 단위**로 삭제
- 토픽 생성 시 `cleanup.policy` 로 정책 지정
  - `delete`: 일정 시간(`retention.ms`)이나 용량(`retention.bytes`) 초과 시 가장 오래된 세그먼트 삭제
  - `compact`: 같은 key 중 가장 최신 메시지만 남기고 삭제
- **ACTIVE 세그먼트는 삭제 대상에서 제외**

### 컨슈머 오프셋 저장
- 컨슈머 그룹이 파티션의 어디까지 읽었는지 **오프셋을 커밋**
- 커밋된 오프셋은 내부 토픽 `__consumer_offsets` 에 저장
- 컨슈머는 저장된 오프셋을 토대로 다음 레코드를 가져온다

### 그룹 코디네이팅
- 컨슈머 그룹 상태를 체크하고 파티션을 각 컨슈머에 매칭
- **Rebalance**: 컨슈머가 그룹에 들어오거나 빠지면 파티션을 다시 분배

> cf) 오프셋 조회 시 특수값: `-1` = 가장 최신(latest) 오프셋, `-2` = 가장 오래된(earliest) 오프셋
> (`kafka-get-offsets.sh --time -1 / -2`)

## 3. 토픽과 파티션

- **토픽**: 데이터를 구분하는 단위
- **레코드**: 프로듀서가 전달한 데이터 한 건
- **파티션**: 토픽은 1개 이상의 파티션을 가짐. 큐와 비슷하지만 **컨슈머가 가져가도 삭제되지 않는다** →
  목적이 다른 여러 컨슈머 그룹이 같은 데이터를 여러 번 읽을 수 있음

### 파티션 배치 방식
- 0번 브로커부터 **라운드로빈**으로 리더 파티션 배치 → 특정 브로커로 통신이 몰리는 것을 방지
- 팔로워 파티션은 리더 브로커 번호 + 1, + 2 … (`% 브로커 수`) 위치에 배치

```
Broker 0           Broker 1           Broker 2
P0 (Leader)        P0                 P0
P1                 P1 (Leader)        P1
P2                 P2                 P2 (Leader)
```

### 리더 파티션 쏠림
- 원인: 처음에 브로커 1대로 시작했거나, 특정 key 로 데이터가 몰리는 경우
- 문제: 일부 브로커에 컨슈머·프로듀서·팔로워 요청이 과도하게 집중
- 해결: `kafka-reassign-partitions.sh` 로 리더 파티션 재분배

### 파티션 개수와 컨슈머 처리량
- **한 파티션은 (같은 그룹 내) 최대 한 개의 컨슈머**와만 연결
  - 컨슈머가 여러 개라도 파티션이 1개면 나머지 컨슈머는 놀게 된다
  - 파티션이 여러 개인데 컨슈머가 1개면 그 컨슈머가 모든 파티션을 처리
- 분산 처리를 하려면 **파티션과 컨슈머를 함께** 늘려야 한다
- **[주의] 파티션 개수는 줄일 수 없다.** 줄이려면 여러 브로커에 흩어진 데이터를 다시 취합·정렬해야 하므로 지원하지 않음. 신중하게 늘릴 것.

## 4. 레코드

```
┌───────────┬────────┬─────────┬─────┬───────┐
│ Timestamp │ Offset │ Headers │ Key │ Value │
└───────────┴────────┴─────────┴─────┴───────┘
```

- 프로듀서가 레코드를 생성해 브로커로 전송 → **브로커가 오프셋과 타임스탬프를 지정**해 저장
- 한 번 적재된 레코드는 **수정 불가**. 리텐션 기간 / 용량에 의해서만 삭제

| 필드 | 설명 |
| --- | --- |
| Timestamp | 기본은 프로듀서의 생성 시각(`CreateTime`). 토픽 설정 `message.timestamp.type=LogAppendTime` 으로 브로커 적재 시각 사용 가능 |
| Offset | 0부터 1씩 증가. **브로커가 생성**하므로 프로듀서에는 없는 정보. 파티션마다 독립적인 오프셋을 가짐. 컨슈머는 이걸로 처리한/처리할 레코드를 구분 |
| Headers | 스키마 버전 등 부가 정보 |
| Key | **파티셔닝 기준**. 해시값으로 특정 파티션에 매핑 → 같은 key 는 같은 파티션 → **순서 보장**. `null` 이면 여러 파티션에 분산 |
| Value | 실제 데이터. 보통 JSON 문자열로 직렬화해 저장하고 컨슈머가 역직렬화 |

## 5. 메타데이터

- 클라이언트는 **리더 파티션이 어느 브로커에 있는지** 알기 위해 브로커에게 메타데이터를 요청
- 리프레시 관련 옵션
  - `metadata.max.age.ms`: 메타데이터 강제 리프레시 간격
  - `metadata.max.idle.ms`: 사용하지 않는 토픽의 메타데이터를 유지하는 시간
  - 너무 짧으면 과도한 요청, 너무 길면 변화를 즉시 파악하지 못함
- 브로커 중단 / 리더 재배치로 메타데이터가 현실과 다르면 → 클라이언트가 잘못된 브로커에 요청 →
  `NotLeaderOrFollowerException`, `LeaderNotAvailableException` 등이 발생 → **자동으로 메타데이터 갱신 후 재시도**

## 6. 프로듀서

- 전송할 데이터를 선언하고 특정 토픽의 파티션으로 전송
- **리더 파티션을 가진 브로커와 직접 통신**

| 옵션 | 설명 |
| --- | --- |
| `bootstrap.servers` | 브로커 주소 목록. 일부 브로커 장애에 대비해 2개 이상 지정 |
| `key.serializer` / `value.serializer` | key / value 직렬화 클래스 |
| `acks` | 전송한 데이터가 정상 저장되었는지 확인하는 수준 |

`acks`

| 값 | 의미 | 용도 |
| --- | --- | --- |
| `0` | 저장 여부를 확인하지 않음 | 유실보다 속도가 중요한 경우 (예: GPS 데이터) |
| `1` | 리더 파티션에 적재되었는지만 확인 | 가장 많이 사용 |
| `-1` / `all` | 리더 + ISR 팔로워 모두 적재 확인 | 가장 안정적 (`min.insync.replicas` 와 함께 사용). Kafka 3.0+ 기본값 |

## 7. 컨슈머

- 브로커로부터 데이터를 가져와 처리

| 옵션 | 설명 |
| --- | --- |
| `bootstrap.servers` | 브로커 주소 목록 (2개 이상 권장) |
| `key.deserializer` / `value.deserializer` | key / value 역직렬화 클래스 |
| `group.id` | 컨슈머 그룹 아이디 |
| `auto.offset.reset` | 그룹에 **커밋된 오프셋이 없을 때** 어디서부터 읽을지. `latest`(기본) = 가장 최근부터, `earliest` = 가장 오래된 것부터 |

### 컨슈머 그룹
- 여러 컨슈머가 메시지를 나눠 처리하도록 묶은 그룹 → 병렬성과 확장성 향상
- 그룹 내 각 컨슈머는 1개 이상의 파티션을 할당받음
- **한 파티션은 같은 그룹 안에서 오직 하나의 컨슈머에만 할당**
- 컨슈머가 추가/제거되면 파티션이 자동 재분배(리밸런스)되어 부하를 균등하게 유지

### Consumer Lag
```
                CURRENT-OFFSET              LOG-END-OFFSET
                (커밋된 위치)                 (마지막 레코드 + 1)
offset: 0 1 2 ... 9 │ 10 11 ... 19   20 21 │
                    └──── CONSUMER LAG ────┘
```
- `LAG = LOG-END-OFFSET - CURRENT-OFFSET`
- 모니터링해서 LAG 이 계속 늘어난다면 처리량이 부족한 것 → **파티션과 컨슈머를 함께 증가**
